# Solar PV Design Platform v2.0 Alpha 1 Migration Notes

## Migration policy

v2.0 Alpha 1 preserves supported project lineage and refuses unknown schemas. Migration is deterministic and must not silently change the engineering rule basis.

The v2 project schema is `2.0`. The rule-pack schema is separately versioned as `2.0.0`; the two version domains are not interchangeable.

## Supported incoming project schemas

The v2 core retains the v1.9-supported migration lineage, including:

- `1.9`
- `1.8`, `1.8-final`, `1.8-rulepacks`
- supported v1.7 variants (including `1.7-alpha6` and earlier supported aliases)
- supported v1.6 lineage already retained by v1.9

An unsupported/unknown schema is rejected rather than coerced or guessed.

## v1.9 projects

A v1.9 project with engineering-rule configuration is migrated through `SolarPVRulePackContract.migrateV19EngineeringRuleConfiguration()`.

The migration:

1. validates the historical overlay for unsafe/prototype-pollution and immutable-identity paths;
2. resolves the original configuration with the frozen v1.9 rule engine;
3. converts the configuration to a strict-v2 or frozen-legacy-overlay policy as applicable;
4. rebuilds the rule context through the v2 compatibility adapter;
5. compares the pre/post v1.9 `rule-xxxxxxxx` fingerprint;
6. rejects the migration with `RULE_BASIS_DRIFT` if the fingerprint changes;
7. stores explicit migration provenance, rule-pack schema version, contract fingerprint and compatibility mode.

If the v1.9 snapshot already stores a rule fingerprint, project migration verifies it against the rebuilt compatibility context before accepting the migrated snapshot.

## v1.8 projects

Projects carrying explicit v1.8-style engineering rule configuration preserve the selected base pack and rule settings. The configuration is normalized into the v2 contract provenance model while the frozen v1.9 compatibility calculation basis is retained. Rule-level tests exercise v1.8-style explicit pack migration without compatibility fingerprint drift.

## v1.7 / older supported projects

Older supported projects without explicit engineering-rule configuration continue to migrate to `SPVDP-LEGACY-V17`. Historical detailed-electrical form inputs are supplied as legacy compatibility inputs so they remain the basis for resolved design-current/current-density/voltage-drop/temperature assumptions.

The resulting project stores explicit v2 migration provenance while retaining the legacy compatibility calculation result and fingerprint.

## Historical v1.9 metadata overlays

v1.9 allowed project overlays to modify several metadata fields that v2 treats as immutable engineering-pack provenance. To avoid silently changing historical projects, Alpha 1 does not reinterpret or discard such overlays.

Instead, a historical overlay containing those legacy metadata paths is migrated to `overlayPolicy: "legacy-v1.9-frozen"` with a migration-time `legacyOverlayFingerprint`. The v2 compatibility adapter rejects any later mutation of that frozen object. Users may clear/recreate the overlay under the strict v2 allow-list if they intentionally want an editable v2 overlay.

## New strict v2 overlays

New/editable overlays use `overlayPolicy: "strict-v2"`. Only explicitly allowed v1.9 compatibility paths may be modified. Pack identity/version/schema, provenance, review/approval/claim status, compatibility declarations, and capabilities are immutable through project overlays. Unknown safety-critical paths and `__proto__` / `prototype` / `constructor` are rejected.

Numeric engineering values must be JSON numbers; string-to-number coercion is not permitted.

## Revision/history behavior

Migration does not rewrite an already stored immutable historical revision in place. The imported/restored source snapshot is validated/migrated in memory; any later save/commit creates current-schema state according to the existing immutable revision/repository semantics.

Revision numbers, project IDs, parent fingerprints, project fingerprints, local-first storage behavior, the HTTP repository contract, SQLite immutable revisions, and the existing database filename remain part of the retained continuity model.

## Opening/saving/reopening a v2 project

A current-schema v2 snapshot must include engineering-rule configuration and formal provenance. Validation rebuilds the compatibility context and verifies, when present/required:

- the v1.9 compatibility fingerprint;
- rule-pack schema version `2.0.0`;
- formal contract fingerprint;
- the configured overlay policy/frozen-overlay fingerprint.

A mismatch is rejected rather than silently repaired.

## Engineering claim boundary after migration

Migration establishes software provenance and compatibility; it does not upgrade preliminary v1.9 assumptions to validated standards content. A migrated project remains distinguishable from a future native independently reviewed/validated pack through compatibility mode, lifecycle/claim state, capability state, evidence references, and both fingerprint namespaces.
